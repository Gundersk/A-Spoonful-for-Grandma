# Совместная работа

Один репозиторий. main — согласованная база; сдаваемые версии — теги/релизы. Долгоживущие отдельные ветки дизайнера/программиста не нужны. Основная доска задач — YouGile. Новая задача: карточка YouGile → ветка `feature/recipe-book`, `feature/inventory`, `fix/...` или `art/...` → Pull Request → проверка → merge. Исторический первый импорт ещё требует ручного Preview; не считать main автоматически подтверждённой сборкой.

## Взять задачу

Прочитать STATUS/ROADMAP, согласовать scope и владельца сцены/спрайта. В чистой папке: `git switch main`, `git pull --ff-only`, `git switch -c feature/<задача>`. При чужих изменениях не использовать reset/clean. Разные JS-модули можно править параллельно; один Layout/объект Construct лучше назначать одному участнику. Для истории использовать свой Git user.name/email, не чужие данные.

## Сделать и передать

Закрыть проект в Construct, сделать резерв/commit, выполнить задачу. Обновить STATUS/CHANGELOG и нужные реестры в том же изменении. `npm run assets` обновляет техническую часть ASSETS; ручное назначение объектов/права/источники не выводятся из PNG автоматически. `npm run check`, `npm test`, при структуре MCP validate_project. Снова открыть Construct, выполнить соответствующий сценарий TESTING; записать реальный результат. Посмотреть git diff и git status, исключить случайные материалы. `git add <нужные-пути>`, `git commit`, `git push -u origin <ветка>`, открыть PR по шаблону.

При остановке посередине заполнить docs/handoffs/<дата>-<задача>.md по шаблону; отметить выполненное/непроверенное, точку продолжения, команду и ветку. Сохранить рабочую ветку на сервере, не переносить её в main как готовую. В PR указать, что авторство/проверки конкретного человека не заменяются обещаниями ИИ.

## Контроль учёта

CI выполняет проверку нативной структуры, полигоны, тесты и сравнение изменений с документацией. Игровая правка требует STATUS+CHANGELOG; структура объектов — OBJECTS; графика — ASSETS; новый модуль — ARCHITECTURE. Проверяется наличие обновления, а не его правдивость: это смотрит ревьюер. Необязательные задачи фиксировать в YouGile; ROADMAP хранит направления и зависимости, GitHub Issues — технические обсуждения/ссылки, не раздувать scope.

Владелец в Settings → Rules/Branches по возможности настраивает запрет прямого push в main, PR и обязательный check `project`. Доступность/применение защиты для private-репозитория зависит от аккаунта/тарифа; если функция недоступна, соблюдать правило командой. Создание файлов workflow само по себе не включает защиту. Для этого репозитория 01.11.2026 защита main отдельно настроена через GitHub API: PR, один approval, review владельца по CODEOWNERS, обязательный check project, запрет force-push/удаления. Enforce admins выключен: владелец-администратор может осознанно обойти правила, например для аварийного восстановления. Рекомендован один reviewer — владелец или второй программист. При squash merge сохранять в описании PR участников и факт AI assistance, если это требуется учебными правилами.

## Откат и возвращение владельцу

Готовый плохой коммит отменяется `git revert <hash>` в отдельной fix-ветке и PR; не переписывать общую историю force-push. Перед откатом несохранённых файлов сделать копию. Для продолжения на ПК владельца — сохранить свои изменения, pull --ff-only main либо checkout согласованной ветки, прочитать STATUS/HANDOFF, повторить проверки; MCP локально перенастраивается на этот game/.

## Дизайнер

Основная карточка предложения — в YouGile; файлы можно хранить в art/proposals/<имя> и art-ветке/PR, технические вложения/обсуждение — в связанном Issue при необходимости. Загрузка не меняет игру автоматически. Статус обсуждения фиксировать в карточке YouGile и README предложения. Разделение источников/игровых кадров описано в DESIGNER.md.

## Связь с YouGile

В описании PR указывать URL/ID карточки YouGile и scope/критерии; в карточке — обратную ссылку на ветку/PR/commit. В commit допустимо короткое ID; в HANDOFF — полный URL и текущий этап. При завершении обновить карточку и документы; при остановке оставить следующий шаг и проверенные/непроверенные части. URL доски и её названия статусов пока не предоставлены — не изобретать. Старые Issues1–3 сохраняются как технические ссылки, не создают вторую независимую очередь.

Предложения дизайнера/владельца можно прикреплять в YouGile; для хранения в Git использовать art/proposals или art/references со ссылкой на карточку. Issue допускается как техническое обсуждение/вложение с обратной ссылкой YouGile, а не обязательная замена основной доски. Согласованное решение отражать в design-документах, чтобы ИИ мог прочитать его без доступа к доске/переписке.
