# Устройство прототипа

Нативный папочный проект Construct 3; движок отвечает за EightDir/Solid, экземпляры Sprite/Text, анимации, слои и ввод. Игровые правила находятся в JS-модулях, зарегистрированных в project.c3proj. `main.js` имеет purpose=main; остальные purpose=none. Bootstrap пустой. Никакой самостоятельной Canvas-игры рядом нет.

| Модуль в game/scripts | Ответственность и связи |
|---|---|
| main.js | runOnStartup → beforeprojectstart создаёт Input, KitchenState, Player, CameraController, Interactions, HUD, ThrowController. Связывает события и мышь. |
| input.js | Снимки клавиш и pressed/down; клавиатура через runtime.keyboard. |
| player.js | PlayerBody.Move8.simulateControl в pretick; направление по скорости, выбор анимации Grandma и зеркалирование. |
| camera.js | Конфигурация камер по именам Layout. Static/Follow, clamp по viewport; независимая прокрутка UI. Kitchen static. |
| data.js | RECIPE/POT/ECONOMY, COUNTER, SLOTS, STATIONS, PLACEMENT_SURFACES. Не дублировать их числа в новых модулях. |
| state.js | KitchenState — единственный источник логических состояний кастрюли/запасов/показателей; act/tick/pickUp/drop. |
| economy.js | Денежная награда от вккал. При 10 ложках 100 вккал и 10 монет, при одной — 10 и 1. |
| interactions.js | Ближайшая станция, E/Q, canReachPot по близости предмета с учётом высоты поверхности. Читает реальные объекты. |
| throw.js | Бросок и геометрия физического основания; readSurfaces, syncServingSurface, contact, placement. Вызывает state.act при посадке. |
| hud.js | Отображение показателей/подсказок/таймера и PotVisual, порядок отрисовки. Не хранит независимое состояние игры. |

## Порядок кадра

pretick: синхронизация поверхности стола, опрос клавиатуры, симуляция управления. tick: state.tick (dt ограничен 0.1), throw.tick (свой дробный шаг), взаимодействия, визуал бабушки, камера, HUD. ЛКМ обрабатывается mousedown: курсор читается отдельно в UI и World; панели UI исключаются из броска. При рефакторинге сохранять порядок и не перезапускать текущую анимацию каждый кадр.

## Кастрюля и рецепт

pot.location: counter / hands / floor / flight / BurnerSlot_1 / BurnerSlot_2 / ServingSlot_1. pot.content: empty / raw / washed / ready. spoons — целое 0..10; fill вычисляется, не накапливается float. visualState: empty или content_low/medium/full. remaining — таймер, served — защита от повторной награды. После подачи кастрюля визуально остаётся; следующее взятие очищает её. В варке/полёте подобрать нельзя. Добавление сырой крупы к washed снова требует мойки; в ready добавить нельзя. Стартовые container=30, bag=120 ложек; пополнение контейнера из мешка сейчас автоматическое, покупок нет.

## Пространство и поверхности

PlayerBody — точка ног и физическое тело. Grandma — визуал, PotVisual при переносе рисуется на y-132. CounterZone/Slot-маркеры — подходы бабушки; CounterSurface/StoveSurface/ServingSurface — реальные места посадки, не области пола перед ними. Их границы читаются из экземпляров. ServingSurface следует за отдельным ServingTableVisual; Solid-блокер стола автоматически за ним не движется.

Бросок разделяет плоскость ground(x,y) и высоту z; экран = (x,y-z). У плиты/столешницы elevation=72, у стола=32. Дальность 220 от ног. Входящий боковой контакт отличается от начального перекрытия; верхняя посадка на спуске по высоте. Контакты сортируются по времени, затем по минимальному сдвигу внутрь поверхности; центр не выходит за дальность/назад. Основание кастрюли width×height/2. Counter фиксирует y и учитывает препятствие-банку. См. DECISIONS и TESTING.

## Расширение

Не вводить второй источник истины для кастрюли в инвентаре или UI. Будущая книга рецептов должна читать данные рецептов; будущий инвентарь потребует отдельно согласованной модели, а не трактовки hands как готового инвентаря. Сейчас state/main ориентированы на одну кухню/один предмет. CameraController допускает разные Layout, но это не система переходов. Новые события, автоматика, концовки в следующих этапах должны иметь отдельные модули. API проверять по официальной документации Construct, а не по предположениям MCP.

## Переноска вниз

player.js выбирает generated-набор для W/E/SW/SE и дополнительно только для carrying+S. carry_walk_S_generated содержит 4 кадра/8fps/loop; старый carry_walk_S однокадровый и архивный. При остановке остаётся carry_idle_S, без предмета walk_S. Воспроизведение запускается только при смене имени, не каждый tick. Добавление кадров выполнено через исправленный MCP; отдельные объекты персонажей не созданы.
