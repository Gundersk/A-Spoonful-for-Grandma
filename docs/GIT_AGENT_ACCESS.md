# Доступ разработчика и агента к GitHub

Для команды рекомендуем локальный агент + обычный Git-доступ разработчика. Отдельный GitHub-аккаунт для ИИ не требуется. Владелец приглашает **человека**, тот принимает приглашение, авторизуется своим GitHub на своём ПК и своим аккаунтом в ИИ-клиенте. Агент выполняет разрешённые Git-команды в этом окружении от имени разработчика. Это обычный авторизованный доступ, не обход прав.

## Три независимые настройки

| Настройка | Что даёт | Чего не даёт сама по себе |
|---|---|---|
| GitHub collaborator с правом записи | Права человека на репозиторий/свои ветки | Не авторизует автоматически Git, ИИ или приложение на его ПК |
| Локальная авторизация GitHub через GCM/CLI/SSH | Git может отправлять изменения с правами этого аккаунта | Не предоставляет подписку/доступ к модели; не отключает защиту main |
| Вход в ChatGPT/Codex/другой ИИ-клиент и разрешения среды | Модель/инструменты и разрешённая работа с файлами/командами | Вход OpenAI не является входом GitHub; обычное чтение репозитория не доказывает push |

Construct MCP — четвёртая отдельная часть: он редактирует локальную папку game/, **не выдаёт GitHub-права и не делает commit/push автоматически**. Его установка описана в MCP_SETUP.md.

## Вариант A — локальный агент, рекомендуемый для Construct

1. Владелец добавляет GitHub-аккаунт участника в Settings → Collaborators с правом записи. Участник принимает приглашение. Публичность позволяет читать/скачивать, но не даёт посторонним право прямой записи.
2. Участник устанавливает Git. На Windows используйте Git for Windows с Git Credential Manager(GCM); при авторизации GCM открывает браузер, человек сам проходит вход/2FA. Данные сохраняются в системном хранилище. Наличие GitHub Desktop/входа на сайте не считать доказательством авторизации конкретного Git в терминале.
3. Клонировать репозиторий и открыть **его корень**, а не game/, в агентном клиенте. Логин модели выполнить своим аккаунтом. Установить исправленный MCP с разрешения по SETUP/MCP_SETUP, если нужны структурные правки.
4. Настроить авторство Git **локально для репозитория** (свои имя и email, можно GitHub noreply). Это подпись истории, а не выдача прав:

```powershell
git config --local user.name "Ваше имя"
git config --local user.email "Ваш подтверждённый email или GitHub noreply"
git status
git fetch origin
```

5. Выполнить обычную задачу в feature/fix/art-ветке: агент обновляет код/реестры/статус, запускает проверки, показывает diff, создаёт commit и делает `git push -u origin <ветка>` в рамках разрешения задачи. На первом требующем авторизации HTTPS-запросе Git может открыть GCM-вход. Пользователь вводит пароль/2FA в официальном окне, **не в чате с ИИ**. Публичный clone/fetch может пройти вообще без входа — это не проверка прав записи.
6. По успешному push агент сообщает ветку/commit; открывается PR по WORKFLOW. main остаётся защищённым, merge/релиз — отдельный этап. Право записи не означает право менять настройки/обходить review.

Для создания PR из терминала можно отдельно установить/авторизовать GitHub CLI (не обязательно для git push): `gh auth login`, выбрать GitHub.com, HTTPS, вход через браузер и согласиться на авторизацию Git. `gh auth status` показывает аккаунт/статус; токен в чат не выводить. CLI не устанавливается автоматически этим документом. SSH — допустимая альтернатива HTTPS, отдельная настройка ключа пользователем по официальным GitHub Docs.

Права/CLI могут быть настроены при помощи агента, но браузерный вход/2FA и подтверждение OAuth пользователь проходит сам. Не использовать общий пароль владельца/общий токен команды. Если доступ выдан другому аккаунту, войти нужным, а не менять только user.name. Не выполнять `git credential fill` ради вывода токена и не помещать credentials в remote URL, .env, коммит или handoff.

## Вариант B — облачная задача Codex

Разработчик входит в свой аккаунт ChatGPT, создаёт/выбирает облачное окружение, подключает свой GitHub, выбирает доступный репозиторий и проверяет предложенные права интеграции. При запросе установки/одобрения приложения, который он не может выполнить, помогает владелец репозитория или администратор организации. Само приглашение Collaborator не устанавливает GitHub-приложение и не гарантирует, что конкретный репозиторий появился в облачном клиенте.

Облачная задача работает в своём окружении: локальные GCM/Construct/PWA/MCP с ПК туда автоматически не переносятся. Проверить возможность сборки MCP/доступность Git-инструментов отдельно; доступ к файлам на ПК и ручной Construct Preview не обещать. Для этого проекта облако подходит для кода/документов/тестов, а окончательная приёмка Construct остаётся отдельной. Сначала проверить, какие операции текущая интеграция реально поддерживает (чтение, запись, ветка, PR), затем выдавать задачу. Доступность зависит от клиента/аккаунта/настроек организации.

## Обычный ChatGPT и другие агенты

Подключённый GitHub в обычном чате, публичная ссылка и режим Codex — не одно и то же. Интеграция, предоставляющая только поиск/чтение, не сможет выполнить push: одного входа/ссылки недостаточно. Проверять реальные инструменты, не обещать запись по значку «подключено». Для правок используйте поддерживающий редактирование агентный клиент или облачное coding-окружение. Для локального клиента **GitHub-коннектор в ChatGPT необязателен**, если уже есть локальный Git, доступ к папке, авторизация и разрешение на команды/сеть.

Другой агент может работать тем же способом через локальный Git от имени участника. Если его сервис использует GitHub App/OAuth/MCP для записи, подключение настраивается у этого участника отдельно; правила установки приложения/организации сохраняются. Отдельный бот/сервисный аккаунт возможен для будущей централизованной автоматизации, но сейчас не настроен и команде не нужен.

## Разрешение на автоматическое завершение задачи

Пример запроса агенту (использовать, только если участник согласен с перечисленными действиями):

> Прочитай AGENTS.md и профильные документы. По карточке YouGile <URL/ID> выполни задачу. В рамках этой задачи разрешаю создавать рабочую ветку, изменять нужные файлы, обновлять обязательную документацию, запускать проверки, создавать коммиты, отправлять свою ветку в origin и открывать Pull Request. Сначала проверь аккаунт, remote и чужие изменения. Не меняй main, релизы, чужие ветки или настройки доступа без отдельной задачи. В конце сообщи commit, ветку, PR, проверки и следующий шаг.

Такое разрешение снимает необходимость отдельно просить каждый рутинный commit/push этой задачи. Но ограничения клиента/песочницы/сети могут требовать пользовательского подтверждения: не отключать их автоматически и не советовать безусловный полный доступ. AGENTS/CI не являются фоновым агентом: без запущенного агента и задания сами отчёты/коммиты не появляются.

Логирование — STATUS/CHANGELOG/OBJECTS/ASSETS и при остановке HANDOFF; автор/время/дифф — Git; задача — YouGile со ссылкой PR. Не записывать только «сделано»: указывать проверки, непроверенный Preview и следующий шаг. Не создавать пустые коммиты ради демонстрации push. При отказе отправки сохранить локальную работу и сообщить **«commit локально, push не выполнен»**, не объявлять её загруженной в GitHub. Push не обновляет Release assets.

## Диагностика

| Симптом | Проверить |
|---|---|
| Репозиторий читается, push403/permission denied | Принято ли приглашение, правильный ли GitHub-аккаунт, права интеграции/организации; public fetch не доказывает запись |
| Git пишет author identity unknown | Свои local user.name/email; это отдельный вопрос от входа GitHub |
| main отклоняет push/review required | Отправить feature-ветку и PR, сохранить защиту; не выдавать агенту admin ради обычной задачи |
| Агент видит файлы, но не запускает Git/сеть | Инструменты/разрешения конкретного клиента и рабочего каталога; не менять глобальные политики вслепую |
| Облако не видит репозиторий | Подключённый GitHub, разрешённый список репозиториев, принятие приглашения, одобрение App администратором при необходимости |
| Подключён MCP, но GitHub недоступен | Это независимые соединения; проверить Git отдельно |
